# 写文档的方法

写或改这个仓库的文档时，按下面的顺序做。

## 第一步：确定读者

每篇文档只有一类读者。先确定读者是谁，只写这个读者需要的内容。别的读者需要的内容放到别的文档里，用一句话指过去。

| 文档 | 读者 | 写什么 | 不写什么 |
|---|---|---|---|
| `README.md` | 第一次接触、想用这个项目的人 | 项目能做什么、怎么用 | 设计、实现细节、开发过程 |
| `docs/deploy.md` | 安装和维护的人 | 步骤、必须遵守的规则、排查方法 | 为什么这样设计 |
| `docs/adr/*.md` | 要理解或修改设计的人 | 背景、目标、现在的设计和理由、限制 | 操作步骤、做的过程 |
| `docs/roadmap.md` | 想知道往哪做、做到哪的人 | 方向、每一项的状态、接下来做什么 | 已完成各项的设计细节 |

判断一句话该不该留：这个读者不读这句话，会不会做错事或理解错。不会就删掉，或挪到对应的文档。

## 第二步：按结构写

### 通用的写法

- **开头先给结论**：这篇文档讲什么，现在的状态是什么。
- **一节只回答一个问题**。小标题直接写这个问题或结论。
- **列表项不超过两句**。超过时拆成子项，或改成表格。
- **需要对比的内容用表格**：多个对象的同几个属性、状态清单、「现象 / 原因 / 处理」。
- **步骤用编号**，命令放在代码块里。
- **只写确定的事实**。没有验证的内容集中放在一处，标明「没有验证」，不混在正文里。
- **按现状写**。不写将来时（「以后」「下一个 PR」），不写已经过时的状态。
- **用书面语**，不用口语和比喻。
- **不写过程**：谁在哪一轮审查发现的、中间试错的经过、用户选了哪个方案、哪天更正的。这些在 git 历史和 PR 里。
- **不用只有当时的人懂的代号**：`③b`、`M1`、「第 4 块」「PR 3」。要指某件事时，写它是什么。
- **PR 编号**只出现在路线图的「已完成」里。别的文档不写。
- **证据路径**（`docs/e2e/` 下的实测记录、测试文件）集中放在文末的「证据」表里。正文只保留理解内容所必需的引用。
- 引用别的小节时写小节名，例如：见「已知限制」。引用别的文档时写文件名和小节名。

### ADR

```
# ADR-NNN：标题

- 状态：已采纳（日期），内容按当前实现维护
- 读者：……
- 关联：别的 ADR

## 背景        当时面对的问题和约束
## 目标        编号列表
## 设计
### 总览       一张 Mermaid 架构图，加一张表：方面 | 设计
### <主题>     现状，然后是「为什么」
## 没有采用的方案   表：方案 | 不采用的原因
## 已知限制         表：限制 | 说明
## 涉及的文件       表：范围 | 文件
## 重新评估的条件   （有才写）
## 证据             表：结论 | 证据路径（有才写）
```

- 不写「决定」一节。直接写现在是怎么设计的。
- 「总览」里尽量用 Mermaid 图画出整体架构：有哪些部分、谁调用谁、数据和凭据往哪走、边界在哪。
  - 写成 ```` ```mermaid ```` 代码块，GitHub 会直接渲染。结构关系用 `flowchart`，有先后顺序的交互用 `sequenceDiagram`，状态变化用 `stateDiagram-v2`。
  - 一张图只表达一件事，节点控制在十几个以内。画不下时拆成两张，放到对应的主题小节里。
  - 图里的名字和正文、代码里的名字一致（进程、用户、目录、表名）。
  - 图不代替文字：图下面仍然要有总览表或几句说明。图和文字说法不一致时，两处一起改。
  - 设计里没有可画的结构时（例如只是一条规则）不硬画。
- 每个主题先写现状，再用加粗的「**为什么……**」写理由。
- 设计变了就改 ADR，让它始终描述现状。不在末尾追加「后续变化」。
- ADR 001–004 是 PoC 阶段的验证记录，状态行保留这个说明。

### 部署文档

- 按安装者做事的顺序排：须知 → 启动 → 访问 → 日常使用 → 升级和备份 → 排查问题。
- 「不要做 X」的规则可以带一句后果，不展开设计理由。
- 失败的情形汇总在「排查问题」表里：现象 | 原因 | 处理。「现象」写安装者实际看到的东西。
- 每条命令都要能照着执行。照着做不成的步骤，要么补全，要么删掉。

### 路线图

- 「总览」表每项一行：编号、内容、优先级、状态。
- 「进行中」「未开始」每项 2 到 4 条：做什么、现状、开始前要先定什么。
- 已经定下的设计用「已经定的」表；没有定的单独列出。
- 「已完成」表写交付了什么和全部 PR 号，设计细节指向 ADR。
- 编号不重用，不改已有的编号。

### README

- 顺序：一句话说明 → 能做什么 → 怎么运行的 → 快速开始 → 怎么用 → 使用前要知道的限制 → 更多文档。
- 「快速开始」控制在几步之内，照着做能跑起来。
- 细节指向 `docs/deploy.md`、`docs/roadmap.md`、`docs/adr/`。

## 第三步：对照代码核对事实

文档里的事实会过时。改写时原文的说法不能直接照搬。

1. **逐条对照代码**。命令、路径、权限位、默认值、数量上限、步骤顺序、环境变量名，都到代码里确认。
2. **找出原文之后变了的东西**。原文写成之后合并的改动，常常没有写回文档。对每个主题，看一眼对应的代码最近改过什么。
3. **派一个全新的子 agent 做独立核对**，篇幅大或涉及安全的文档必须做（判断标准见 `CLAUDE.md` 的「写文档按 write-docs skill」）。给它新旧两版和要对照的代码位置，让它分别列出：
   - 新版里和代码不一致的；
   - 旧版里有、新版里丢了的事实；
   - 残留的代号、过程叙述、将来时；
   - 文内引用和证据路径是否存在。
4. **没能核实的内容**在 PR 描述的「证明不了的」里逐条写明，不要写成确定的事实。

## 第四步：检查没有破坏引用

- 代码、测试、注释、别的文档会按小节名引用文档。改小节名之前先搜：

  ```bash
  grep -rn "deploy.md\|roadmap.md\|docs/adr" --include=*.ts --include=*.md --include=*.yml --include=*.yaml --include=*.mjs . | grep -v node_modules
  ```

- `docs/deploy.md` 的「### 镜像里有什么」那张表由 `tests/image-probe.test.ts` 核对，表的内容不要改；改了要同时改 `.github/scripts/image-probe-checks.json`。
- 去掉了对某个 `docs/e2e/` 目录的引用后，如果没有别的文档和代码引用它，在同一个 PR 里删掉这个目录。

## 第五步：提交前自查

- [ ] 开头说明了这篇文档讲什么。
- [ ] 每一节的标题和内容相符。
- [ ] 没有超过两句的列表项，没有单行特别长的表格单元格。
- [ ] 没有代号、过程叙述、将来时、口语。
- [ ] 同一件事没有在两处用不同的说法写。
- [ ] 文内的「见『X』」都指向存在的小节。
- [ ] 事实对照过代码；没核实的写进了 PR 描述。
- [ ] 被代码和测试引用的小节名还在。

## PR 描述

按 `CLAUDE.md` 的要求写，另外加两张清单：

- **按现状改掉的内容**：原文怎么写、现在怎么写、依据的代码位置。
- **删掉的内容**：删了什么、为什么。
