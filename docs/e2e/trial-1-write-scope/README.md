# 试用反馈第 1 条：agent 事先知道可写范围（真实模型 E2E）

脚本：`scripts/write-scope-e2e.ts`。用真实的 deepseek-flash 跑内置 standard 工作流。developer 模板的可写范围是 `src/**`、`test/**`、`tests/**`、`docs/changes.md`、`package.json`、`package-lock.json`。需求故意要求把代码写到 `lib/clamp.js`，这个位置在范围外。agent 提问时，脚本记下问题，回答「按你的判断做」。

| 运行 | 代码 | 为路径问用户 | 开发第一次回复越界 | 最终位置 | 任务 |
|---|---|---|---|---|---|
| `before-main.json` | main 2c452ac（改动前） | **问了**（评审阶段：「实现路径需要由你决定：规格要求 lib/clamp.js，但可写范围不含 lib/\*\*」） | 越界（`lib/clamp.js` 被撤销） | — | 记下提问后停止 |
| `after-1-first-wording.json` | 9c80886（第一版措辞） | 没问 | 越界，下一轮自己改到 `src/` 并说明 | `src/clamp.js` | 完成，6/7 |
| `after-2.json` | 9a61f6b（最终措辞） | 没问 | **没越界**，回复写明「需求/规格点名 lib/clamp.js……改放到 src/clamp.js」 | `src/clamp.js` | 完成，8/8 |
| `after-3.json` | 9a61f6b（最终措辞） | 没问 | 越界，并自称「符合可写范围」；撤销后下一轮改到 `src/` | `src/clamp.js` | 完成，6/8 |

## 结论

- 能证明：改动后 3 次运行都没有为路径问用户，都在范围内完成。改动前同样的需求会让 agent 来问用户。
- 能证明：可写范围出现在开发会话的第一条提示词里（每份报告的第一项检查）。
- 不稳定的部分：开发第一次回复就放对位置，最终措辞下 2 次里只有 1 次。另一次是规格作者先把 `lib/clamp.js` 写进了验收标准，开发照着写，还误判自己没越界。之后靠平台撤销和撤销后的说明在下一轮纠正。规格作者不知道开发的可写范围，这是剩下的原因。
- 样本量：每种代码只跑了 1 到 2 次，比例只能说明有这种现象，不能当成比率。

## 运行方式说明

- 改动前那次用的是第一版脚本：调用进行中被提问时会卡住。第一次提问（规格阶段，问的是 NaN 怎么处理）由人手动回答。第二次提问就是表里那个路径问题，记下后停掉了进程，所以任务状态是 failed。之后的脚本改成调用进行中也能自动回答。
- `run-after2.log`、`run-after3.log` 是命令行输出。
