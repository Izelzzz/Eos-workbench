# ADR-002：团队约定放在平台里，交付物由平台检查

- 状态：已接受（2026-11-20）
- 关联：ADR-001（平台与执行内核）

## 背景

- Agent 提升了个人效率，但团队交付没有同步变快：每个人用不同的 agent 和工作方式，交付物的格式和完整度各不相同，成本转移到了互相审查质量参差的 AI 产出上。
- ADR-001 的工作流只描述"谁按什么顺序做"，没有描述"每个阶段必须交出什么"。阶段之间是否合格全靠下游 agent 或评审去发现。
- 团队的研发约定散落在各自的提示词和习惯里，没有一份所有 agent 共用、可以追溯版本的约定。

## 目标

1. 团队把从规格到交付的流水线配置成工作流，写明每个阶段的交付物和验收条件。
2. 阶段之间的验收由平台用程序检查，不靠模型自评。不合格就带着原因退回同一个 agent，超过次数再问人。
3. 团队约定文档注入到任务里每个 agent 的会话里，所有成员发起的任务按同一份约定执行。
4. 约定可以在网页上维护，每次修改都有版本；每个任务记录它用了哪一版，出问题时能追溯。

## 决定

1. **约定存在平台的数据库里**，不放在代码仓库里。`conventions` 表只追加：工作流（YAML）和约定文档（Markdown）每次保存都是一个新版本，最新版本即生效版本。内置模板和文档在平台上没有时写成第 1 版，之后不覆盖团队的修改。
2. **任务创建时快照**：解析工作流和它 `docs` 引用的文档的最新版本，存进任务状态；任务元数据记录用到的版本号。之后修改约定不影响进行中的任务。
3. **交付物和检查写在工作流节点上**：`deliverables`（文件路径 + 必须包含的 Markdown 章节）和 `checks`（命令，退出码为 0 才算通过）。平台在 worktree 里执行，结果作为事件交给引擎。
4. **引擎的 outbox 从"一个调用"扩展为"调用或检查"**，引擎仍然是纯函数：
   - agent 节点：产出后跑检查；不通过把原因交给同一个 agent 补齐，最多 `maxFixes` 次（默认 2），用完问用户。
   - 对话节点：每一轮先跑检查，通过后才请评审方；评审方可以省略，此时检查通过即本轮通过。检查失败和评审意见一样计入轮次，沿用 5 轮 → 上游重新确认 → 问用户的规则。
5. **约定文档注入在每个会话的第一条消息**，放在角色说明之前；同一会话里不重复。
6. 内置「标准交付」（`standard`）工作流：规格 → 开发 → 测试 → 评审 → 交付，交付命令是占位，由团队在约定页替换。

## 为什么这样做

- **放平台而不是仓库**：约定是团队级的，一个团队有多个仓库；放在某个仓库里要么重复、要么需要跨仓库引用。平台上能直接做版本、历史和改动对比，第 4 块"自我改进"的改进提案也能直接写回平台、走审批，而不必给每个仓库开 PR。代价是约定和代码不在同一个版本库里，见下面"重新评估的条件"。
- **程序检查而不是模型自评**：模型自评会"觉得写完了"。文件是否存在、章节是否齐全、测试是否通过可以用程序确定地判断，判断结果能直接给出原因交回 agent。需要判断质量的部分仍交给评审方。
- **检查走 outbox 而不是在 runner 里顺手做**：检查结果决定流程走向（退回、计轮次、问人），放进引擎才能被状态空间穷举和变异测试覆盖；runner 只负责执行，崩溃后重跑检查即可（检查没有副作用）。
- **快照而不是引用**：任务可能跑几十分钟，期间约定被修改，任务前后半段用不同的约定会让结果无法解释。
- **评审方可选**：测试阶段本质是"命令失败 → 开发修"的对话，没有必要请一个模型来转述测试输出；省掉一次模型调用，也避免模型误读失败原因。

## 影响范围

- 工作流 schema：节点新增 `deliverables`、`checks`、`maxFixes`；对话节点的 `role` 改为可选；工作流新增 `docs`。旧的工作流 YAML 仍然合法。
- 引擎：`Task.pending` 的类型从 `Call` 改为 `Call | CheckRun`，新增 `checked` 事件、`fix` 用途、`Task.docs`、`Task.fixes`、`DialogState.review`。之前保存的任务读出时补默认值。
- 存储：新增 `conventions` 表；`TaskMeta.conventions` 记录用到的版本。
- runner：新增检查执行器 `src/runner/checks.ts`。
- Web：新增「团队约定」页和 `/api/conventions` 接口；新建任务默认用 `standard`；trace 里新增"检查"类型的 span。
- 命令行：`eos run` 的 `--workflow` 先按平台上的工作流名查找，找不到再按 YAML 文件路径加载（文档仍从平台取）。

## 安全与已知限制

- **检查命令不在 agent 的沙箱里**：命令以平台进程的权限在 worktree 里执行，等同于 CI runner。`npm test` 会执行 agent 改过的 `package.json` 脚本，所以只给检查命令最小的环境变量（PATH、HOME、LANG、LC_ALL、TMPDIR、TZ，加 `CI=1`），不传模型密钥。仍然能读写平台用户能访问的文件。第一版只面向个人和小团队的本机部署；多人部署前需要把检查放进沙箱。
- **改工作流等于决定平台在本机执行什么命令**：能保存约定的人就能让平台以平台用户的身份运行任意命令。第一版靠"只监听本机地址 + 写接口要求同源"把这限制在本机用户自己；开放给团队访问之前，约定的修改必须有登录、权限和审批。
- 交付物路径在解析时限制为 worktree 内的相对路径，执行时再挡住指向 worktree 外面的符号链接。
- 约定的修改没有审批：任何能打开页面的人都能保存新版本。审批放到第 4 块（自我改进）和多用户支持里。
- 章节检查只看 Markdown 标题是否包含章节名，不判断内容质量；质量由评审方判断。

## 重新评估的条件

- 团队希望约定和代码一起评审、一起回滚：考虑把平台约定同步到仓库（或从仓库导入），平台仍保留版本记录。
- 多用户部署：检查命令必须进沙箱，约定修改需要权限和审批。
- 检查类型不够用（例如需要调用外部服务验证）：再增加检查种类，而不是让模型自评。
