# ADR-002：团队约定放在平台里，交付物由平台检查

- 状态：已采纳（2026-11-20）。PoC 阶段的验证记录；和 `docs/roadmap.md` 冲突时以路线图为准
- 读者：要理解团队约定和阶段检查的人
- 关联：ADR-001（平台结构）、ADR-003（Agent 模板）、ADR-004（改进提案和审批）

## 背景

- agent 提高了个人效率，但团队交付没有同步变快。每个人使用不同的 agent 和工作方式，交付物的格式和完整度各不相同，成本转移到了互相审查质量参差的 AI 产出上。
- 只描述「谁按什么顺序做」的工作流，没有描述「每个阶段必须交出什么」。阶段之间是否合格，只能靠下游的 agent 或评审去发现。
- 团队的研发约定分散在各人的提示词和习惯里，没有一份所有 agent 共用、可以追溯版本的约定。

## 目标

1. 团队把从规格到交付的流水线配置成工作流，写明每个阶段的交付物和验收条件。
2. 阶段之间的验收由平台用程序检查，不依靠模型自评。不合格时带着原因退回同一个 agent，超过次数再问人。
3. 团队约定文档注入到任务里每个 agent 的会话，所有成员发起的任务按同一份约定执行。
4. 约定可以在网页上维护，每次修改都有版本。每个任务记录它用了哪一版，出问题时能追溯。

## 设计

### 总览

| 方面 | 设计 |
|---|---|
| 存放 | 平台的数据库，表 `conventions`，只追加 |
| 版本 | 每次保存是一个新版本，最新版本即生效版本 |
| 任务 | 创建时快照用到的约定，并记录版本号 |
| 检查 | 交付物和检查命令写在工作流节点上，由平台在 worktree 里执行 |
| 注入 | 约定文档放在每个会话的第一条消息里 |

### 约定存在平台的数据库里

- 工作流（YAML）和约定文档（Markdown）都存在 `conventions` 表里。Agent 模板和技能也存在这张表里（ADR-003）。
- 内置的工作流和文档在平台上不存在时写成第 1 版，之后不覆盖团队的修改。

**为什么放在平台而不是代码仓库**

- 约定是团队级的，一个团队有多个仓库。放在某个仓库里，要么重复，要么需要跨仓库引用。
- 平台上能直接做版本、历史和改动对比。
- 改进提案（ADR-004）能直接写回平台并走审批，不必给每个仓库开 PR。
- 代价：约定和代码不在同一个版本库里。

### 任务创建时快照

- 创建任务时，平台解析工作流和它 `docs` 引用的文档的最新版本，存进任务状态。
- 任务元数据记录用到的版本号。
- 之后修改约定不影响进行中的任务。

**为什么用快照而不是引用**：任务可能运行几十分钟。期间约定被修改时，任务前后半段使用不同的约定，结果无法解释。

### 交付物和检查

工作流节点上可以写两类验收条件：

| 字段 | 内容 | 通过条件 |
|---|---|---|
| `deliverables` | 文件路径，以及文件必须包含的 Markdown 章节 | 文件存在，章节齐全 |
| `checks` | 命令 | 退出码为 0 |

平台在 worktree 里执行检查，结果作为事件交给引擎。

`checks` 里还可以写**平台动作**：`{ platform: push }` 推送任务分支，`{ platform: pull-request }` 开 PR。平台动作由平台用自己持有的凭据完成，规则如下：

- 只能放在没有评审角色的对话节点里，并且前面必须有带评审角色的对话节点。
- 必须排在命令检查之后。前面的检查不通过时不执行。
- 失败时不交回 agent、不计轮次，任务失败，等人重试。
- 平台动作有副作用，所以实现成重复执行结果相同。

**为什么用程序检查而不是模型自评**

- 模型自评会「觉得写完了」。
- 文件是否存在、章节是否齐全、测试是否通过，可以用程序确定地判断，判断结果能直接作为原因交回 agent。
- 需要判断质量的部分仍然交给评审方。

### 检查在引擎里的位置

引擎的待执行项是「调用或检查」两种之一。引擎仍然是纯函数。

| 节点类型 | 检查的时机 | 不通过时 |
|---|---|---|
| agent 节点 | agent 产出之后 | 把原因交给同一个 agent 补齐，最多 `maxFixes` 次（默认 2）。用完后问用户 |
| 对话节点 | 每一轮先执行检查，通过后才请评审方 | 和评审意见一样计入轮次：打满轮次（默认 5）→ 上游重新确认 → 问用户 |

- 对话节点的评审方可以省略。省略时，检查通过即本轮通过。
- 命令检查没有副作用，平台崩溃后重跑即可。

**为什么检查由引擎调度，而不是 runner 顺带执行**：检查结果决定流程走向（退回、计轮次、问人）。放进引擎，才能被状态空间穷举和变异测试覆盖。

**为什么评审方可以省略**：测试阶段本质上是「命令失败，开发修复」的对话。请一个模型转述测试输出没有必要，省掉一次模型调用，也避免模型误读失败原因。

### 约定文档的注入

约定文档放在每个会话的第一条消息里，位于角色说明之前。同一个会话里不重复注入。

### 内置的「标准交付」工作流

`standard` 工作流的阶段是：规格 → 开发 → 测试 → 评审 → 交付。交付阶段是平台动作 `pull-request`。新建任务默认使用 `standard`。

### 检查命令的运行环境

- 检查命令不在 agent 的沙箱里运行，相当于 CI runner。`npm test` 会执行 agent 改过的 `package.json` 脚本。
- 因此检查命令只得到最少的环境变量，不包含模型 key 和主密钥。完整的变量清单和 Docker 部署下的独立用户见 ADR-006。
- 交付物路径在解析时限制为 worktree 内的相对路径，执行时再拒绝指向 worktree 外面的符号链接。
- 解析时还有两条校验：写交付物的角色不能是只读的；交付物必须在这个角色的 `writePaths` 之内。
- 章节检查只看 Markdown 标题是否包含章节名，不判断内容质量。质量由评审方判断。

## 已知限制

| 限制 | 说明 |
|---|---|
| 修改工作流等于决定平台执行什么命令 | 能保存约定的人，就能让平台运行任意检查命令 |
| 手动修改约定没有审批 | 没有登录，能打开页面的人都能保存新版本。agent 的改进提案有审批（ADR-004）。现有的缓解措施：平台默认只监听本机地址，写接口要求同源 |
| 不用 Docker 部署时，检查命令以平台的用户运行 | 能读写平台用户能访问的文件。Docker 部署下它以独立用户运行（ADR-006） |
| 约定和代码不在同一个版本库 | 不能一起评审、一起回滚 |

前两项依赖登录和多人（路线图第 7 项）才能解决。

## 涉及的文件

| 范围 | 内容 |
|---|---|
| 工作流 schema | 节点的 `deliverables`、`checks`、`maxFixes`；对话节点的 `role` 可选；工作流的 `docs` |
| 引擎 | 待执行项是调用或检查；`checked` 事件；`fix` 用途 |
| 存储 | `conventions` 表；任务元数据里的 `conventions` 记录用到的版本 |
| runner | `src/runner/checks.ts` |
| Web | 「团队约定」页和 `/api/conventions` 接口；trace 里「检查」类型的 span |
| 命令行 | `eos run` 的 `--workflow` 先按平台上的工作流名查找，找不到再按 YAML 文件路径加载。文档仍从平台读取 |

## 重新评估的条件

- 团队希望约定和代码一起评审、一起回滚：考虑把平台的约定同步到仓库，或从仓库导入，平台仍保留版本记录。
- 检查的种类不够用（例如需要调用外部服务验证）：增加检查种类，不改成模型自评。
