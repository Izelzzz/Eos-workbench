# ADR-004：Agent 自我改进——从任务记录归纳改进提案，经人审批写回团队约定

- 状态：已接受（2026-11-21）
- 关联：ADR-002（团队约定放在平台里）、ADR-003（团队级 Agent 模板）

## 背景

- 第 1 到 3 块之后，团队约定（工作流、约定文档、Agent 模板、技能）放在平台上、只追加、带版本，任务记录用了哪一版；
  每个任务的日志里有评审意见、检查结果、补齐和重新确认，`metrics.ts` / `insights.ts` 能按阶段和模板统计成本和瓶颈。
- 但这些信号只停留在"看得到"：同一类评审意见反复出现、同一条检查反复失败，要靠人自己翻任务、自己想该改哪份约定。
- ADR-002 约定：改进提案直接写回平台上的约定并**走审批**；约定修改目前没有审批，留给本块（ADR-002「安全与已知限制」、ADR-003 末条）。

## 目标

1. 从任务记录里用程序归纳证据：评审要求修改的意见、检查失败、回复格式重试、对话打满轮次请上游重新确认、走到尽头问用户、越界撤销、调用失败。
   每条证据能链回任务和日志条目，并归到它涉及的约定（模板、技能、约定文档、工作流）。
2. 由一个只读的 `improver` Agent 读证据和约定的当前内容，产出改进提案：改哪个约定、基于第几版、改成什么、理由、依据哪些证据。
   平台在边界校验：新内容能通过这类约定的保存校验，引用的证据必须真实存在。
3. 提案经人审批：批准后生成约定的新版本（备注写明提案号）；拒绝、过期都留记录。没有批准的提案不改任何约定。
4. 网页上能看提案、证据（链回任务）、新旧内容对比，并批准或拒绝。
5. 能按版本对比改进前后用了这份约定的任务的指标。

验收标准（用户已确认）：

1. 证据归纳是纯函数、有单测，每条证据可追溯到任务和日志条目。
2. `improver` 模板只读、不能联网和跑命令；它的输出在边界解析，不合格的提案不入库并记原因。
3. 提案状态只追加（待审批 → 批准 / 拒绝 / 过期）；批准时目标约定已经不是提案基于的版本，就拒绝批准并标为过期；进行中的任务不受影响（仍用创建时的快照）。
4. 未批准的提案不改变任何约定（有测试）。
5. `#/improve` 页面：提案列表、证据、新旧对比、批准 / 拒绝。
6. 改进前后对比：按任务快照里的版本号分组，比较 token、agent 时长、评审轮次、检查失败、补齐次数、完成率；任一组少于 3 个任务标「样本不足」。
7. 真实模型 E2E 跑完整流程：一组任务 → 生成提案 → 批准 → 新任务用上新版本 → 对比页能看到两组。

## 决定

1. **证据由程序归纳，模型只负责"怎么改"**（`src/engine/evidence.ts`，纯函数）。
   - 证据（signal）的种类和来源（都来自引擎写下的日志，不再问模型）：
     - `review_changes`：评审调用的回复解析为 `changes`；内容是评审结论和问题清单；
     - `check_failed`：一次检查里没通过的每一条，内容是检查描述和原因（截断）；
     - `format_retry`：评审或上游重新确认的回复无法解析；
     - `escalated`：对话打满轮次，请上游重新确认；
     - `stuck`：流程走到尽头，问用户（检查补齐用完、对话重新确认后仍不通过）；
     - `scope_reverted`：调用之后有越界改动被撤销；
     - `call_failed`：调用失败。
   - 每条证据有稳定、唯一的 id（`任务:日志下标`；检查失败再带 `:第几条`，越界撤销带 `:r`），记下节点和**被评判的角色**：
     评审意见、对话里的检查失败和打满轮次算到被评审方（对话的 `with` 节点的角色），agent 节点的检查失败算到这个节点的角色；
     上游重新确认后决定问用户的算到上游的角色，其余问用户按所在节点算；格式重试算到给出这个回复的角色，越界撤销算到这次调用的角色。
     agent 在调用中途主动提问是正常的澄清，不算证据。
   - 打满轮次和调用失败按引擎写的说明识别，说明的文字由 `machine.ts` 导出、两边共用。
   - 归到约定：有角色的证据归到这个角色的模板和技能；所有证据都归到任务用的工作流和约定文档。按约定汇总时，"用到它的任务数"把没有出问题的任务也算进去，作为分母。
2. **提案单独存，状态只追加**：新表 `proposals`（目标约定的种类和名字、基于的版本、新内容、理由、引用的证据 id、生成范围、生成调用的模型和用量）和 `proposal_events`（状态变化、时刻、操作者、原因、批准后生成的版本号）。提案的当前状态是最后一条事件。
3. **批准在一个事务里完成**：读目标约定的最新版本 → 不等于提案基于的版本就记「过期」并拒绝 → 用约定的保存校验再校验一次 → 写新版本（备注 `改进提案 #<id>：<理由摘要>`）→ 记「已批准」和新版本号。手动在团队约定页保存照旧直接生效，不走审批（见「已知限制」）。
4. **生成提案手动触发**：网页上或 `eos improve --workflow <名> [--tasks <id,…>]`。平台先算证据，把证据、相关的指标和瓶颈、目标约定的当前内容放进提示词，交给内置 `improver` 模板。
   - `improver`：`write: none`，去掉全部工具组（web、subagent、bash、schedule、todo、goal），不挂技能和 MCP；会话的工作目录是平台数据目录里的一个空目录。只通过现有的执行器接口调用，不改 `src/executor/dsh.ts`。
     平台只从这个模板里取模型、effort 和提示词，权限按上面写死：团队在约定页改了 improver 模板也放不开它的权限。
   - 候选约定只有这次证据涉及、并且有证据的（最多 6 个）；提示词里列出的证据最多 40 条，提案只能引用列出的证据。
   - 输出格式：最后一个 ```json 代码块，`{ proposals: [{ target: { kind, name }, content, rationale, evidence: [id…] }] }`，一次最多 3 条。
   - 边界校验（`src/improve/`）：JSON 结构（zod）→ 目标约定属于本次候选 → 引用的证据 id 都在本次列出的证据里、至少一条 → 同一个约定只有一条 →
     **不改权限**（模板的 model、write、writePaths、tools、mcp；工作流里角色的这些字段、新增可写或挂 MCP 的角色、检查命令）→ 内容和当前版本不同、通过这类约定的保存校验。
     不合格的提案不入库，原因记在这次生成的结果里返回给调用方（命令行逐条打印）。
   - 权限相关的修改只能由人在团队约定页手动改：提案经人批准后，平台会以平台用户的权限执行工作流的检查命令、给 agent 更大的写入范围，
     这些不应该由模型提出、靠审批的人逐行看出来。
   - 没有证据时不调用模型。
   - 命令行：`eos improve`、`eos proposals`、`eos approve <提案号>`、`eos reject <提案号> "<理由>"`。
5. **前后对比按版本分组**（纯函数）：对一个约定的某个版本 v（通常是批准生成的版本），用了这份约定的任务里，版本 < v 的是「改进前」、≥ v 的是「改进后」；任务用的版本从任务元数据 `conventions` 读（模板版本也在任务快照里）。比较每个任务的 token、agent 时长、评审轮次、检查失败次数、补齐次数和完成率（完成 / 已结束）；进行中的任务不计入。任一组少于 3 个任务时只列数字，标「样本不足」，不下结论。

## 为什么这样做

- **证据用程序归纳**：评审结论、检查结果、重新确认都是引擎已经确定判断过的结构化事实，再交给模型去"读日志找问题"既贵又可能漏、可能编。程序归纳的证据有稳定 id，提案引用 id，平台能核对"依据"是不是真的。模型只做程序做不了的部分：从一组意见里归纳出约定该怎么写。
- **提案单独存，而不是直接存成约定的"草稿版本"**：约定表的语义是"最新版本即生效版本"（ADR-002），往里放未批准的内容会让每个读约定的地方都要先过滤状态。单独的表让"没批准就不改约定"由结构保证。
- **基于版本 + 过期**：提案是针对某一版写的完整新内容；目标在这期间被人改过，直接批准会悄悄覆盖别人的修改。过期后重新生成，成本是一次模型调用。
- **提案是完整的新内容，不是补丁**：约定的保存校验针对完整内容；审批页做新旧对比即可。补丁要再定义一套格式和冲突规则。
- **improver 只读、无工具**：它读的证据里有评审意见和检查输出，内容来自仓库和其他 agent，可能夹带指令。只读、不能跑命令和联网，它能做的最坏的事就是写出一条坏提案，而提案必须经人批准。
- **手动触发**：每次生成是一次模型调用，自动触发要做调度、去重和"同一问题不反复提案"，留到之后。
- **按版本分组对比**：任务快照里已经记了版本号，不需要额外记录"哪个任务在改进之后"。

## 安全与已知限制

- **手动保存不走审批**：没有登录，审批分不清是谁批的，给手动修改加审批只是多一次点击。审批只对 Agent 提案生效；多用户部署时手动修改也要改成提案。操作者只记来源（`web` / `cli`），不是具体的人。
- **批准工作流提案等于批准平台执行它的检查命令**（ADR-002）：所以提案不能改检查命令和权限字段，生成时就拒绝（见决定 4）。约定文档和技能的内容没有这层限制，它们只影响 agent 读到的说明。
- 同一次生成的提案共用一次模型调用，提案上记的用量和时长是整次调用的（`generator.run` 相同）。
- **证据归到约定文档和工作流是粗粒度的**：一条评审意见会归到任务用的所有约定文档上，不代表是这份文档的问题；模板和技能按角色归，精确一些。
- 校验只保证提案能保存、引用的证据存在，不保证改得对；改得对不对由审批的人判断，事后看前后对比。
- 前后对比是相关不是因果：两组任务的需求不同、模型有随机性，样本少时差异可能完全是噪声。只在每组至少 3 个任务时给出比较，仍需人判断。
- 证据里的检查输出截断到固定长度，太长的失败原因只保留开头和结尾。
- 一次生成只看给定的工作流和任务范围；跨工作流共用的模板，在别的工作流里的表现不在这次证据里。

## 重新评估的条件

- 多用户部署：手动修改也走提案和审批，审批记录具体的人。
- 提案经常因为"过期"作废：考虑改成补丁格式并自动合并。
- 有足够多的任务样本：考虑自动触发和统计显著性检验。
