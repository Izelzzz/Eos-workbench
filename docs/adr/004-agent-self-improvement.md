# ADR-004：改进提案——从任务记录归纳证据，经人审批写回团队约定

- 状态：已采纳（2026-11-21）。PoC 阶段的验证记录；和 `docs/roadmap.md` 冲突时以路线图为准
- 读者：要理解证据归纳、改进提案、审批和前后对比的人
- 关联：ADR-002（团队约定）、ADR-003（Agent 模板）

## 背景

- 团队约定（工作流、约定文档、Agent 模板、技能）放在平台上，只追加、带版本，任务记录用了哪一版。
- 每个任务的日志里有评审意见、检查结果、补齐和重新确认。平台能按阶段和模板统计成本和瓶颈。
- 这些信号只停留在「看得到」：同一类评审意见反复出现、同一条检查反复失败时，要靠人自己翻任务、自己判断该改哪份约定。

## 目标

1. 用程序从任务记录里归纳证据。每条证据能链回任务和日志条目，并归到它涉及的约定。
2. 由一个只读的 `improver` agent 读证据和约定的当前内容，产出改进提案：改哪个约定、基于第几版、改成什么、理由、依据哪些证据。
3. 提案经人审批。批准后生成约定的新版本；拒绝和过期都留记录。没有批准的提案不改变任何约定。
4. 网页上能查看提案、证据、新旧内容对比，并批准或拒绝。
5. 能按版本对比改进前后使用这份约定的任务的指标。

## 设计

### 总览

| 步骤 | 由谁完成 | 位置 |
|---|---|---|
| 归纳证据 | 程序（纯函数） | `src/engine/evidence.ts` |
| 生成提案 | `improver` agent，手动触发 | `src/improve/` |
| 校验提案 | 程序 | `src/improve/` |
| 审批 | 人 | 网页 `#/improve` 或命令行 |
| 前后对比 | 程序（纯函数） | `src/engine/compare.ts` |

**为什么证据由程序归纳，模型只负责「怎么改」**

- 评审结论、检查结果、重新确认都是引擎已经确定判断过的结构化事实。再让模型去读日志找问题，成本高，还可能遗漏或编造。
- 程序归纳的证据有稳定的 id。提案引用 id，平台能核对依据是否真实存在。
- 模型只做程序做不了的部分：从一组意见里归纳出约定该怎么写。

### 证据

证据都来自引擎写下的日志。

| 种类 | 来源 |
|---|---|
| `review_changes` | 评审调用的回复解析为 `changes`。内容是评审结论和问题清单 |
| `check_failed` | 一次检查里没通过的每一条。内容是检查描述和原因（截断） |
| `format_retry` | 评审或上游重新确认的回复无法解析 |
| `escalated` | 对话打满轮次，请上游重新确认 |
| `stuck` | 流程走到尽头，问用户（检查补齐用完，或对话重新确认后仍不通过） |
| `scope_reverted` | 调用之后有越界改动被撤销 |
| `call_failed` | 调用失败 |

agent 在调用中途主动提问是正常的澄清，不算证据。

**id**

每条证据有稳定、唯一的 id：`任务:日志下标`。检查失败再加 `:第几条`，越界撤销加 `:r`。

**归到哪个角色**

| 证据 | 归到 |
|---|---|
| 评审意见、对话里的检查失败、打满轮次 | 被评审的一方（对话的 `with` 节点的角色） |
| agent 节点的检查失败 | 这个节点的角色 |
| 上游重新确认后决定问用户 | 上游的角色 |
| 其余的问用户 | 所在节点的角色 |
| 格式重试 | 给出这个回复的角色 |
| 越界撤销 | 这次调用的角色 |
| 调用失败 | 不归到角色，只归到工作流和约定文档 |

**归到哪个约定**

- 有角色的证据归到这个角色的模板和技能。
- 所有证据都归到任务使用的工作流和约定文档。
- 按约定汇总时，「用到它的任务数」把没有出问题的任务也计入，作为分母。

打满轮次和调用失败按引擎写下的说明文字识别。说明文字由 `machine.ts` 导出，两边共用。

### 提案的存储

| 表 | 内容 |
|---|---|
| `proposals` | 目标约定的种类和名字、基于的版本、新内容、理由、引用的证据 id、生成范围、生成调用的模型和用量 |
| `proposal_events` | 状态变化、时刻、操作者、原因、批准后生成的版本号 |

- 状态只追加：待审批 → 批准、拒绝或过期。提案的当前状态是最后一条事件。
- 提案是完整的新内容，不是补丁。

**为什么单独存，而不是存成约定的草稿版本**：约定表的语义是「最新版本即生效版本」（ADR-002）。往里放未批准的内容，每个读约定的地方都要先过滤状态。单独的表让「没批准就不改约定」由结构保证。

**为什么是完整内容而不是补丁**：约定的保存校验针对完整内容，审批页做新旧对比即可。补丁需要另外定义格式和冲突规则。

### 生成提案

手动触发：在网页上，或用 `eos improve --workflow <名> [--tasks <id,…>]`。没有证据时不调用模型。

1. 平台计算证据。
2. 平台把证据、相关的指标和瓶颈、目标约定的当前内容放进提示词，交给内置的 `improver` 模板。
3. 平台校验 `improver` 的输出，合格的提案入库。

| 上限 | 数值 |
|---|---|
| 候选约定（这次证据涉及、有证据、并且平台上存在的；来自 YAML 文件的工作流不算） | 6 个 |
| 提示词里列出的证据 | 40 条 |
| 一次生成的提案 | 3 条 |

输出格式：回复里带 `proposals` 数组的最后一个 JSON 对象（通常写在 `json` 代码块里），结构是 `{ proposals: [{ target: { kind, name }, content, rationale, evidence: [id…] }] }`。

同一个数据目录同一时间只运行一次生成，用锁保证。

**为什么手动触发**：每次生成是一次模型调用。自动触发需要调度、去重和「同一问题不反复提案」，没有做。

### `improver` 的权限

- `write: none`，去掉全部工具组，不挂技能和 MCP。
- 会话的工作目录是平台数据目录里的一个空目录。
- 平台只从这个模板里读取模型、effort 和提示词，权限固定如上。团队在约定页修改 `improver` 模板，也放不开它的权限。
- dsh 的文件工具和向用户提问的工具不属于任何工具组，去不掉（ADR-003）。因此 **`improver` 只要调用了任何工具，整次生成作废，不入库**。已经执行的工具和模型发出的工具调用都算。

**为什么只读、无工具**：它读的证据里有评审意见和检查输出，内容来自仓库和其他 agent，可能夹带指令。只读、不能执行命令和联网时，它能做的最坏的事是写出一条坏提案，而提案必须经人批准。

### 提案的校验

按顺序检查，不合格的提案不入库，原因记在这次生成的结果里返回。

1. JSON 结构合法。
2. 目标约定属于本次的候选。
3. 引用的证据 id 都在本次列出的证据里，至少一条。
4. 同一个约定只有一条提案，一次最多 3 条。只计已经入库的：前一条被拒绝时，同一个约定后面合格的那条仍可入库。
5. 不改权限。
6. 内容和当前版本不同，并且通过这类约定的保存校验。

「不改权限」的规则：

- 模板的 `model`、`write`、`writePaths`、`tools`、`mcp` 不能变。`effort`、`skills`、`prompt` 不在核对范围内。
- 工作流里已有角色的这些字段不能变。
- 新增的角色，这些字段必须和原工作流里某个已有的角色完全相同。
- 已有的节点不能换成权限不同的角色；新增的节点只能使用已有权限的角色。
- 检查命令（包括超时）和平台动作不能变。平台动作连同它前面有哪些评审节点一起比较。

约定文档和技能的内容没有这层限制：它们只影响 agent 读到的说明。

**为什么提案不能改权限**：提案经人批准后，平台会执行工作流的检查命令、给 agent 更大的写入范围。这些不应该由模型提出、再靠审批的人逐行看出来。权限相关的修改只能由人在团队约定页手动完成。

### 审批

批准在一个事务里完成：

1. 读目标约定的最新版本。不等于提案基于的版本时，记为「过期」并拒绝批准。
2. 用约定的保存校验再校验一次，并重新执行权限核对。不通过时不批准，提案保持待审批，不记事件。
3. 写入新版本，备注是 `改进提案 #<id>：<理由摘要>`，后面可以跟审批人的备注。
4. 记「已批准」和新版本号。

- 进行中的任务不受影响，仍然使用创建时的快照。
- 命令行：`eos proposals`、`eos approve <提案号> ["<备注>"]`、`eos reject <提案号> "<理由>"`。

**为什么基于版本并会过期**：提案是针对某一版写的完整新内容。目标在这期间被人修改过时，直接批准会覆盖别人的修改。过期后重新生成，成本是一次模型调用。

**为什么批准时再核对一次权限**：生成之后，工作流引用的模板可能被人改过。同一份内容展开出来的权限会变。

### 前后对比

对一个约定的第 v 版：

- 使用第 v-1 版的已结束任务是「改进前」；
- 使用第 v 版的已结束任务是「改进后」。

只比较相邻的两版，这样变化只来自这一次修改。任务使用的版本从任务快照和任务元数据读取。

| 指标 | 说明 |
|---|---|
| token | |
| agent 时长 | |
| 评审轮次 | 有效结论的次数，格式重试不算 |
| 检查失败 | |
| 补齐次数 | agent 节点的 fix 调用：检查没通过后的补齐，以及按用户指示的调整 |
| 证据条数 | |
| 完成率 | 已完成 ÷（已完成 + 已中止），变化按百分点 |

| 任务的情况 | 处理 |
|---|---|
| 进行中 | 不计入 |
| 失败后还没处理（可能重试） | 单独列出，不计入 |
| 版本未知（例如工作流来自 YAML 文件） | 单独列出 |
| 任一组少于 3 个任务 | 只列数字，标「样本不足」，不计算变化 |

统计页列出每条已批准提案的对比，提案详情页也显示。

**为什么按版本分组**：任务快照里已经记录了版本号，不需要额外记录「哪个任务在改进之后」。

### dsh 注入的指令文件

dsh 会把指令文件注入 agent 的会话，平台保留这个行为。dsh 读取三类文件：

| 来源 | 文件 |
|---|---|
| 从会话的工作目录往上，到第一个含 `.git` 的目录为止（找不到时只看工作目录本身） | 每一级的 `AGENTS.md`、`CLAUDE.md`、`AGENTS.local.md`、`CLAUDE.local.md` |
| 会话中途 agent 的文件工具访问到的子目录 | 工作目录到那个子目录之间各级的同名文件 |
| 全局 | 运行 dsh 的用户的 `~/.agents/AGENTS.md`，以及 dsh 数据目录下的 `AGENTS.md`。Docker 部署下运行 dsh 的用户是 `eos-agent`。平台不把 `DSH_AGENTS_HOME` 传给 dsh，所以不能用它改位置 |

- 任务会话的工作目录是 worktree 的根。worktree 的 `.git` 是文件也算，所以只读取仓库自带的。
- `improver` 的工作目录在数据目录里。数据目录位于某个仓库里时，会读到那个仓库的指令文件；否则读不到。

**为什么保留**：仓库自带的说明对任务有用；部署方也可以用全局文件统一补充说明。

## 已知限制

| 限制 | 说明 |
|---|---|
| 手动保存约定不走审批 | 没有登录，审批无法区分是谁批的。审批只对 agent 的提案生效。操作者只记录来源（`web` 或 `cli`），不是具体的人 |
| `improver` 的会话里仍有文件工具和提问工具 | 工具在被调用的那一刻已经执行（能读，不能写，不能联网）。读到的内容只进入被作废的那次回复 |
| 指令文件不在平台的约定版本里 | 任务记录不下它们用了哪一版。因此 `improver`「需要的内容都在消息里」不完全成立 |
| agent 写进 worktree 的指令文件在同一会话的下一步就生效 | dsh 每一步都重新比对这些文件。包括子目录里的和 `.local` 的。超出写入范围的也一样，直到调用结束被平台撤销。写入范围内的还会被同一任务后面的会话读到 |
| agent 删掉 worktree 的 `.git` 后，dsh 会继续往上找指令文件 | 会找到数据目录所在的仓库 |
| 权限核对不完全管「放松评审」 | 工作流提案可以删掉没有检查命令、后面也没有平台动作的评审节点（例如 `feature` 工作流里的）。由提示词约束和审批的人判断 |
| 证据只核对「在本次列出的证据里」 | 不核对是否和目标约定有关。一条提案可以引用只和别的角色有关的证据 |
| 证据归到约定文档和工作流是粗粒度的 | 一条评审意见会归到任务使用的所有约定文档上，不代表是这份文档的问题。模板和技能按角色归，更精确 |
| 校验不保证改得对 | 只保证提案能保存、引用的证据存在。是否改对由审批的人判断，事后看前后对比 |
| 前后对比是相关不是因果 | 两组任务的需求不同，模型有随机性，样本少时差异可能完全是噪声 |
| 同一次生成的提案共用一次模型调用 | 提案上记录的用量和时长是整次调用的 |
| 检查输出被截断 | 太长的失败原因只保留开头和结尾 |
| 一次生成只看给定的工作流和任务范围 | 跨工作流共用的模板在别的工作流里的表现，不在这次的证据里 |

部署时的两条注意事项：不要把数据目录放在别的仓库里；不要在运行 dsh 的用户的 `~/.agents/AGENTS.md` 里放不想让 agent 看到的内容。

## 没有采用的方案

| 方案 | 不采用的原因 |
|---|---|
| 让模型读日志找问题 | 成本高，可能遗漏或编造，依据无法核对 |
| 提案存成约定的草稿版本 | 每个读约定的地方都要过滤状态 |
| 提案用补丁格式 | 需要另外定义格式和冲突规则 |
| 自动触发生成 | 需要调度、去重和防止反复提案 |
| 关闭 dsh 的指令文件注入，或只读仓库自带的 | 仓库自带的说明对任务有用，全局文件可以用来统一补充说明 |

## 涉及的文件

| 范围 | 内容 |
|---|---|
| 引擎（纯逻辑） | `src/engine/evidence.ts`、`src/engine/compare.ts`。不改状态机 |
| 存储 | `proposals`、`proposal_events` 两张表。约定表不变 |
| 改进服务 | `src/improve/`：提案的解析和校验、生成、审批 |
| 内置模板 | `improver` |
| 命令行 | `eos improve`、`eos proposals`、`eos approve`、`eos reject` |
| Web | `#/improve` 页面和 `/api/improve/…` 接口；统计页的前后对比 |

## 重新评估的条件

- 多人部署：手动修改也走提案和审批，审批记录具体的人。
- 提案经常因为过期作废：考虑改成补丁格式并自动合并。
- 有足够多的任务样本：考虑自动触发和统计显著性检验。
