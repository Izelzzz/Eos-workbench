# Eos 路线图

本文说明 Eos 往哪个方向做、已经做完什么、接下来做什么。优先级于 2026-11-24 确认。

- 产品背景在 Notion 的「Eos 产品文档」。
- 每一项的设计写在 `docs/adr/`，部署方法写在 `docs/deploy.md`。
- 维护方法：每一项拆成几个依次合并的小 PR（见 `CLAUDE.md`）。一项做完时，在「总览」里把状态改成「完成」，并在「已完成」里写上它的全部 PR 号。

## 方向

| 原则 | 含义 |
|---|---|
| 定位 | 团队共用的云端执行环境（所有 agent 的行为对团队可见）+ 平台强制的规则和验收链 + 多角色共用 |
| 押注不变的东西 | 验收标准、程序化的检查、证据链、版本、审批、trace。流水线（规格 → 开发 → 测试 → 评审 → 交付）只是可替换的模板，顺序不固定 |
| agent 在服务端运行 | 实现不依赖「平台和用户在同一台电脑上」 |
| 执行器中立 | 模型质量是硬要求。每家 agent 用它自己最完整的接口，由 `src/executor/types.ts` 的 `Executor` 接口统一。dsh 保留为执行器之一 |
| 凭据只由平台持有 | agent 看不到令牌；提交、推送、开 PR 都由平台完成 |
| 加严容易、放宽要人批 | 新增检查或规则可以由 agent 提出；放宽或删除由人决定 |

ADR 001–004 是 PoC 阶段的验证记录，不作为约束。它们和本文冲突时以本文为准。

## 进行中

### 2. GitHub 接入

- **做什么**：克隆远程仓库、推送任务分支、任务结束时开 PR。`standard` 工作流的交付阶段产出 PR 链接；改动很大时链接到 PR 页面。
- **授权**：GitHub App（按仓库授权、短期令牌、清单流程注册）。设计见 ADR-007。
- **状态**：进行中（克隆 #54、推送 #58、开 PR #60、App 令牌 #63、App 注册页 #66；真实 GitHub App 的注册和 E2E 等第 3 项 PR ③ 合并后做）

## 未开始

### P1

**5. 验收卡点和修正入口**

- 工作流里可以设卡点，指定人或 agent 验收。
- 工作流结束后可以提出改正或补充，不是重做。

**6. 体验小项**

- 指标口径：「已完成调用」改名，并增加工具调用次数、首次响应延迟、缓存命中率。
- span 里的「平台检查」显示检查了什么。
- 各阶段耗时显示阻塞原因。
- span 按类型筛选。

### P2

**7. 登录和多人**

- 开始前要先写方案（ADR）：身份、权限、谁能看到什么。
- 已知的前置问题：任务 ID 由 `Math.random` 生成（`src/runner/supervisor.ts` 的 `newId`）。如果按 ID 控制访问，要先改成 `crypto.randomUUID`。

**8. CI 结果回流和预览链接**

- 统一成「一次提交的外部检查结果」。
- 来源可插拔：GitHub PR 检查（先做）、通用 webhook、查询命令。
- 交付阶段可以回传一组链接（预览地址等），不限定形式。

**9. 带密钥的 MCP 和远程 MCP**

- 现状：模板只支持本地 stdio 的 MCP 服务，不允许放密钥。
- 接上凭据存储后支持 Notion、Figma 等。先做只读。

**10. 测试能力**

- 现状：`standard` 的测试阶段只有一条 `npm test`。
- 做一个测试角色，按类型配技能：单元、属性、集成、契约、API、E2E。
- 每类测试作为一条检查挂在工作流上。适用哪些取决于仓库。

**11. 教训回流**

- 定期复盘已合并的提交和 bug。同类问题出现 2 次写进评审清单，出现 3 次升级进团队约定。参考 yetone/magpie 的 `LESSONS.md`。
- 每条教训包含：规则、原因、证据、出现次数。
- 复用改进提案的审批和前后对比（ADR-004）。
- 先做手动触发，再做定时触发。

**16. 任务之间的隔离**

- 现状：所有任务共用 `eos-check`、`eos-agent` 两个用户和 `eos-work` 组。
  - 一个任务的检查命令和 MCP 服务能改别的任务的 worktree。
  - Landlock 只限制写，agent 能读别的任务的 worktree、仓库和 trace。
- 按任务分组或加 ACL 解决不了。
- 候选方案：检查命令也在 Landlock 里运行（只能写自己的 worktree），或者按任务分配用户。
- 开始前要先写方案。背景见 ADR-006 的「已知限制」。

### P3

**12. 总司令 agent**

- 跨工作流的方案设计和拆分。
- 依赖「项目」这一层，现在没有。
- 可以先做最小版本：把一个大需求拆成几个任务，并选择工作流。

**13. ACP 执行器**

- 通过 Agent Client Protocol 接其他厂商的 agent（Codex、Pi、Gemini CLI 等）。
- 会话续接已有人验证可用。权限按每家自己的机制配置。

**14. 设计系统**

- 界面统一的视觉和组件。

**15. GitLab 接入**

- 在 GitHub 接入之后兼容。

### CI 一项的现状

CI 的目的：把自检清单从「agent 自述」变成「程序证明」。用 GitHub Actions。

| 检查 | 内容 |
|---|---|
| 类型检查、单元测试、构建网页 | 单元测试包含引擎的穷举验证 |
| gitleaks | 扫描密钥泄露 |
| PR 流程检查（pr-checklist） | 按改动路径判断是否需要 E2E；检查描述里的「端到端验证」「能用证据证明的」「证明不了的」几节；核对 E2E 报告所在的提交之后，「需要 E2E」的文件没有再变 |
| lint | ESLint + typescript-eslint。`CLAUDE.md` 的架构约定写成了禁止导入的规则。工具单独装在 `.github/lint/`，因为编译用的 TS 7 没有它需要的 API |
| 格式化 | Prettier，配置在 `.github/lint/prettier.config.json`（printWidth 200） |
| CodeQL | 代码扫描 |
| 依赖扫描 | 只拦截 PR 新引入的高危及以上漏洞，运行时依赖和开发依赖都算 |
| 假模型 E2E | 每个 PR 都运行，不调用真实模型 |
| 镜像 | Trivy 扫描（PR 和发布前都拦截已有修复版本的高危漏洞，豁免逐条写理由和到期日）；容器内的依赖探针（工具、用户、`/data` 的属主）；镜像 ENV 和 dsh 环境白名单的契约测试 |

- 纯文档的 PR 跳过除 gitleaks 和 PR 流程检查之外的检查。
- 真实模型 E2E 的要求不变：改动碰到「需要 E2E」的路径时，仍然要用真实模型运行一次。假模型 E2E 是每个 PR 额外的一道检查，不替代它。

遗留的事项：

| 事项 | 状态 |
|---|---|
| undici 的高危漏洞 | 来自 dsh 的依赖树，等 dsh 发布新的正式版。镜像扫描里逐条豁免，2026-12-25 到期 |
| lint 工具的 7 个中危漏洞（minimatch） | 修复版 typescript-eslint 8.73 发布满两周后升级 |
| CodeQL 的 2 条误报 | 由仓库所有者在 GitHub 上关闭 |
| 任务 ID 用 `Math.random` 生成（CodeQL 告警） | 归入第 7 项 |

## 未排期

**CI**

- 每晚在 main 上用真实模型运行一次 E2E。需要在仓库里配置模型 key 的 secret，并限定在 main 的环境里。按 2025 年的标价粗算，每次约 0.26 美元。
- pr-checklist 按 `CLAUDE.md` 的重档清单提示「这是重档 PR」。

**稳定性**

- Issue #24 的遗留问题，例如中止任务时不会停掉进行中的调用。

**产品**

- 项目级的系统说明和验收标准编号。
- 交付前在合并后的状态上验证。

**部署**

- agent 一侧仍然得到带账号密码的代理地址。检查命令一侧已经不传。

**依赖**

- `vendor/dsh-sdk-client` 换成 npm 上已发布的同版本包。

**出网白名单**

- 现状：agent 和检查命令访问外网不受限制。agent 又能读整个 `/data`（所有仓库、所有任务的 trace），所以代码和 trace 可以被带出去。
- 方向：出口只放行包管理源、模型 API、代码托管，其余默认拒绝。
- 没有定的：
  - 做在哪一层：出口代理、Docker 网络，还是执行器沙箱的网络限制。
  - 名单由谁维护。
  - 要不要按任务或按仓库区分。
- 没有验证的：dsh 和 Claude Code 的沙箱在出口代理下的表现。
